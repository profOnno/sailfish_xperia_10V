# Sailfish OS on Sony Xperia 10 V (Zambezi) - Troubleshooting & Debugging Guide

This document is a collection of troubleshooting steps, diagnostic tools, and log analysis for getting Sailfish OS (Community Port) running on the Sony Xperia 10 V (XQ-DC54 / PDX-235).

## 1. The "Sony Logo" Hang (Mounting Root Failed)

If the device hangs at the Sony logo and fails to boot into the Sailfish UI, the kernel is likely loading, but the `hybris-boot` initramfs cannot hand off to the Sailfish root filesystem.

### Checklist Before Flashing
Ensure your setup matches the known-working configuration:
*   **Stock Base:** Android 14 (`68.1.A.2.270`) or Android 15 (`68.2.A.3.123`).
*   **LineageOS:** 22.2 (Android 15).
*   **Sony Blobs:** `SW_binaries_for_Xperia_Android_13_5.4_v4b_zambezi.img` (This is critical for battery and camera HAL).
*   **Fastboot:** Avoid very new versions (v35+) if flashing fails. Older versions (v33/v34) are sometimes more stable.

### Flashing the Sailfish Images
First, check which slot your device is currently using:
```bash
sudo fastboot getvar current-slot
```
*(The output will likely be `a` or `b`. In the commands below, substitute `<slot>` with the active slot).*

Flash the boot images to the **active slot only**, and the system to the `userdata` partition:

```bash
# Flash boot and dtbo to the ACTIVE slot (e.g., boot_a)
sudo fastboot flash boot_<slot> hybris-boot.img
sudo fastboot flash dtbo_<slot> dtbo.img

# Flash Sailfish system to userdata
sudo fastboot flash userdata sailfish.img001
```

## 2. Capturing Kernel Logs

Because Sony's bootloader blocks `fastboot boot hybris-boot.img --cmdline "bootmode=debug"`, the Telnet debug console is unavailable. 

To debug Sailfish, you must rely on the **persistent kernel log (`pstore`)** from the failed boot attempt, which can be accessed by booting back into **LineageOS Recovery** (Slot A).

**Step 1:** Let the phone hang at the Sony logo (or bootloop).
**Step 2:** Force the phone off (Hold **Power + Volume Up** until it vibrates 3 times).
**Step 3:** Boot into **LineageOS Recovery** (Hold **Volume Down + Power** until the Sony logo appears, then release).
**Step 4:** Connect USB and verify ADB sees the recovery:
```bash
adb devices
```
**Step 5:** Extract the persistent log from the crashed Sailfish kernel:
```bash
adb shell "cat /sys/fs/pstore/console-ramoops*" > pstore_sailfish_crash.log
```
*(If `pstore` is empty, the Sailfish kernel crashed too early to save a log. In that case, the "Sony Logo" hang is a kernel panic before the initramfs even mounts).*

## 3. Analyzing Kernel Logs (LineageOS Baseline)

To prove the hardware is functional before blaming Sailfish, we captured a `dmesg` log from the **working LineageOS 22.2 (Android 14)** system. This log is our "baseline" reference.

*(Note: The log below is from LineageOS, not Sailfish. It is used to compare hardware states.)*

### ✅ Touchscreen (FocalTech)
The LineageOS kernel loads the `fts_ts` driver and detects the panel, proving the hardware is 100% functional:
```
[ 7287.430554] [FTS_TS/I]fts_wait_tp_to_valid:TP Ready,Device ID:0x54
[ 7287.430842] [FTS_TS]fts_ts_resume: Exit(2136)
```
The kernel even logs touch events, confirming the digitizer works:
```
[ 7288.689371] [FTS_TS]fts_input_report_b:[B]P0(526, 2018)[p:46,tm:32] DOWN!
[ 7288.878735] [FTS_TS]fts_input_report_b:[B]P0 UP!
```
**Conclusion:** The "dead screen" in Sailfish is a **Sailfish userspace issue** (Wayland compositor / `libhybris` EGL failing to draw), not a broken touchscreen.

### ⚠️ Audio / DSP (Awinic Amplifier)
The Awinic smart amplifier (`aw882xx`) initializes and starts playback:
```
[ 7289.653421] [Awinic][2-0034]aw882xx_startup: playback enter
```
However, the DSP mixer throws a warning:
```
[ 7289.675593] msm_adsp_init_mixer_ctl_adm_pp_event_queue: failed to get kctl.
```
**Conclusion:** Audio playback works in LineageOS, but the calibration data (`kctl`) for the ADSP is missing. Sailfish may face similar audio issues unless the `v4b` blobs are present.

### 🔋 Battery & PMIC (Charger)
The charger driver is aggressive about resetting the current limit:
```
[ 7289.489188] pm7250b_charger: smblib_set_icl_current: set ICL to 500000uA
```
**Conclusion:** The battery indicator may fluctuate or fail to update in Sailfish. The `v4b` blobs help stabilize this, but some users report the need for a kernel patch to fix the `smblib` (Sony Mobile Battery Interface Lib).

## 4. Automated Diagnostic Script

To gather all hardware data (HALs, inputs, CPU, modules) from a **working LineageOS installation** for comparison, use the `gather_info.py` script included in this repository.

### ⚠️ Critical Prerequisite: Root Access
The script attempts to read `/vendor/firmware/` and run `dmesg`. On a standard LineageOS user build, the `shell` user is blocked from these (you will get a `Permission denied` error). 

You **must** restart the ADB daemon as root before running the script:
```bash
adb root
```
*(If `adb root` fails, ensure "Rooted debugging" is enabled in Developer Options, or you have Magisk installed).*

### 🔒 Privacy & Data Scrubbing
The script has a built-in `--scrub` option. When enabled, it redacts:
*   **MAC addresses** (e.g., `aa:bb:cc:dd:ee:ff` → `XX:XX:XX:XX:XX:XX`)
*   **IPv4 addresses** (e.g., `192.168.1.50` → `X.X.X.X`)
*   **IPv6 addresses** (e.g., `fe80::1234` → `X::X`)

**It is highly recommended to use `--scrub`** if you plan to share the logs publicly (e.g., on GitHub, forums, or in bug reports).

Run the script with scrubbing enabled:
```bash
python3 gather_info.py --scrub
```

If you accidentally run it **without** the flag, the script will print a large warning and pause, giving you a chance to abort. If you proceed without scrubbing, **do not publish the `network_interfaces.txt` file**, as it will contain your Wi-Fi MAC address and local IP addresses in plain text.

### ✅ Verifying the Scrub
After running with `--scrub`, you can verify that the redaction worked by running:
```bash
grep -E "([0-9a-f]{2}:){5}[0-9a-f]{2}|192\.168\.|10\.|172\.(1[6-9]|2[0-9]|3[0-1])\.|([0-9a-f]{1,4}:){2,}" all_diagnostics.txt
```
If the scrub was successful, this command should return **no results**. If it prints any lines, the scrub missed something, and you should not publish the file until it is manually corrected.

## 5. Next Steps for Development

If you are a developer looking to fix the boot hang:

1.  **Compile `libhybris`:** Ensure it supports the `HIDL 4.0` display composer (`vendor.qti.hardware.display.composer@3.0.so`). The stable `libhybris` may be too old.
2.  **Wayland Debugging:** In the Sailfish initramfs, check `/tmp/wayland-0` and `dmesg` for DRM (Direct Rendering Manager) errors. The `drm_notifier_callback` logs indicate the display is waking up, but the compositor is not attaching.
3.  **Battery Fix:** Patch the `smblib` kernel module to not aggressively reset the input current (`set ICL to 500000uA`).
